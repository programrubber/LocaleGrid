IntelliJ Platform 기반 다국어 JSON 관리 플러그인의 로드·편집·검증·저장 기능 및 구현 현황

문서 목적 UI 디자인을 제외한 기능 범위, 처리 규칙, 검증 정책 및 저장 동작의 통합 명세

기술 요약

  • 입력 방식 변화: 기존에는 locale별 JSON을 개별 파일에서 직접 수정하고 같은 key를 파일마다 대조했다. LocaleGrid에서는 하나의 행을 기준으로 locale별 문자열을 연속 입력한다.
  • 통합 로드: 동일 category의 locale JSON을 key 합집합으로 구성하고 중첩 구조를 dot path로 평탄화한다.
  • 편집: 문자열 value, key 추가·이름 변경·삭제, 행 순서 변경을 하나의 편집 모델에서 관리한다.
  • 검증: 저장 차단 Error와 저장 가능한 Warning을 분리하고, BCP 47·Unicode Script 기반 문자 체계 검사를 적용한다.
  • 저장: 대기 입력 반영, 재검증, 메모리 JSON 생성, 대상 파일별 Diff 확인 후 실제 파일을 기록한다.
  • 검증 상태: 프로덕션 Java 33개 파일과 테스트 16개 클래스를 확인했으며 자동 테스트 79건이 통과했다. IDE 수동 실행 검증은 본 보고서 범위에서 제외한다.

02다국어 에디터 및 파일 로드

대상 경로 판정, locale 탐지, key 병합과 dot path 변환의 통합 로드 파이프라인

2.1 대상 파일 판정

지원 디렉터리 및 파일명 패턴
구분패턴판정 규칙
기본 패턴locales/{locale}/{category}.json상위 디렉터리명을 locale, 파일명을 category로 판정
suffix 패턴locales/{locale}/{category}_{locale}.json파일 suffix와 상위 locale 디렉터리명이 일치할 때 suffix를 제외한 이름을 category로 판정
비대상locale root 직하위가 아닌 JSON, 비JSON 파일다국어 에디터 제공 대상에서 제외

대상 JSON을 열면 원본 JSON 탭과 다국어 에디터 탭을 함께 제공한다. category는 현재 열린 파일을 기준으로 고정하고, 동일 파일명 패턴의 sibling locale 파일을 연결한다.

로드 및 병합 규칙
처리 항목규칙결과
자동 locale 탐지locale root 바로 아래 디렉터리명을 후보로 사용ko → en → ja → vi 우선, 그 외 이름순
수동 locale 지정프로젝트 설정의 쉼표 구분 목록을 우선 적용. 현재 연 파일의 locale이 없으면 목록 앞에 포함표시 locale과 열 순서 고정
기준 파일사용자가 현재 연 locale 파일의 key 순서를 우선 사용원본 작업 순서 유지

누락 파일설정된 locale의 category 파일이 없으면 빈 컬럼과 진단을 생성편집 후 저장 시 파일 생성 선택 가능

2.3 Dot Path 변환

중첩 JSON object를 비교 가능한 dot path 행으로 변환하고, 저장 단계에서 다시 중첩 JSON으로 복원한다. 기준 파일의 root entry와 key 순서를 가능한 범위에서 유지한다.

입력 JSON
{
  "login": {
    "title": "로그인",
    "button": "로그인하기"
  }
}
통합 테이블 key
login.title   → 로그인
login.button  → 로그인하기
구조 제약: 빈 key, 선행·후행 점, 연속 점, 공백 segment를 허용하지 않는다. login과 login.title처럼 동일 경로가 문자열 leaf와 object로 동시에 사용되는 경우 Error로 처리한다.

03핵심 편집 기능과 검색·필터

locale별 JSON 직접 입력 방식과 통합 편집 방식의 비교, key·value 편집 및 탐색 기능

3.1 기능 구현 전후의 다국어 입력 방식

기능 구현 전에는 locale별 JSON을 개별 탭에서 직접 수정하고, 파일을 번갈아 보며 같은 key와 누락 값을 대조해야 했다. LocaleGrid는 동일 category의 파일을 하나의 테이블로 연결하여 입력과 저장 전 검토를 같은 흐름에서 처리한다.

JSON 직접 입력 방식과 LocaleGrid 입력 방식 비교
작업 단계기능 구현 전: JSON 직접 입력LocaleGrid 적용 후
파일 준비·열기ko, en, ja 등 locale별 JSON을 찾아 각각 열고 작업 중 탭을 전환대상 JSON 하나를 열면 같은 category의 sibling locale 파일을 자동 탐지·로드
번역값 입력각 파일에서 같은 key 위치를 찾아 문자열 value를 locale별로 개별 수정통합 행을 선택하고 상세 패널에서 locale별 문자열을 연속 입력
key 대조·변경파일별 key 목록을 대조하고 추가·이름 변경·삭제 작업을 각 파일에서 반복key 합집합을 한 표에 표시하고 하나의 key 작업을 통합 변경 상태로 관리
누락·구조 확인특정 locale의 누락 key, 빈 값과 구조 차이를 파일 간 비교로 확인누락·구조·타입·문자 체계 진단을 행과 셀에 연결
저장·변경 검토locale JSON을 파일별로 저장한 뒤 변경 파일이나 VCS Diff를 별도로 검토전체 재검증 후 대상 파일, 변경 건수와 파일별 Diff를 확인하고 저장 승인
비교 기준: 프로젝트 계획과 사용자 문서에 정의된 직접 JSON 편집 문제를 기준으로 정리했다. 시간 절감률이나 오류 감소율과 같은 실측 성과를 의미하지 않는다.

4.3 문자 체계 검사 — Unicode Script

문자열의 실제 언어를 판정하지 않고, locale에서 예상되는 Unicode Script를 기준으로 허용 범위 밖 코드포인트를 탐지한다. 진단에는 key와 locale을 함께 기록하여 셀 단위 확인을 지원한다.

고정 내장 Script 규칙
Locale허용 Unicode Script대표 위반
koHangul, Latin, Common, InheritedHiragana·Katakana, Cyrillic 등
enLatin, Common, InheritedHangul, Kana, Cyrillic 등
jaHiragana, Katakana, Han, Latin, Common, InheritedHangul, Cyrillic 등
viLatin, Common, InheritedHangul, Kana, Cyrillic 등
기타 locale명시 Script subtag 또는 CLDR likely-subtags의 예상 Script + Latin/Common/Inherited결정된 허용 Script 밖 문자
  1. Locale 정규화대소문자와 _/- 구분자를 정규화하고 BCP 47 형식으로 해석한다.
  2. 규칙 선택ko/en/ja/vi 고정 규칙, 명시 Script subtag, CLDR 예상 Script 순으로 허용 집합을 결정한다.
  3. 1차 검사재사용 가능한 Java 정규표현식으로 잠재 위반 문자를 탐지한다. 모든 Unicode 숫자와 U+1F000–U+1FAFF 이모지 범위를 허용한다.
  4. ICU 보완Java 17이 UNKNOWN으로 분류한 코드포인트만 IDE 번들 ICU4J로 교차 확인한다.
  5. Severity 적용프로젝트 설정에 따라 Warning 또는 Error 진단으로 기록한다.
검사 한계: Latin 문자는 제품명·기술 용어 수용을 위해 모든 규칙에서 허용한다. 따라서 영어·프랑스어·베트남어 문장이 ko 또는 ja 값에 들어가도 통과할 수 있다. 일본어와 중국어의 Han 문자도 문자 체계만으로 구분할 수 없다. malformed locale 또는 CLDR에서 Script를 결정하지 못한 locale은 검사하지 않는다.

4.4 예외키 보존

__section__과 같은 root-level 설명·구분 entry를 일반 번역 key와 분리하여 원본 위치와 값을 보존한다.

예외키 처리 방식
구분처리저장 결과
원본 예외키그리드에서 숨기고 key, value, 인접 non-exception root entry를 anchor로 기록anchor가 유지되는 범위에서 root 위치 복원
사용자 추가 예외키현재 편집 중에는 일반 행처럼 표시하고 value 편집·삭제·이동 허용root-level entry로 기록 후 재로드 시 hidden marker로 전환

적용 범위설정 목록과 정확히 일치하는 root-level key만 대상중첩 경로의 동일 이름은 일반 번역 key로 처리

05저장 프로세스

대기 입력 확정부터 검증, 미리보기, 사용자 승인, 파일 기록까지의 저장 단계

5.1 저장 흐름

  1. Flush검색 입력과 상세 value 편집의 debounce 대기 작업을 즉시 반영한다.
  2. Validate소스 진단, key 구조, 누락, 타입, 문자 체계를 전체 재검증한다. Error가 존재하면 즉시 중단한다.
  3. 파일 생성 결정값이 입력된 누락 locale 파일이 있으면 생성 여부를 사용자에게 확인한다.
  4. Previewlocale별 JSON을 메모리에서 생성하고 대상 파일, 변경 현황, 변경 전·후 Diff를 구성한다.
  5. 사용자 승인미리보기 확인 후 적용 또는 닫기를 선택한다. 닫을 경우 프로젝트 파일은 변경하지 않는다.
  6. Write승인된 파일을 IDE 쓰기 명령으로 기록하고 VFS 갱신 후 테이블을 다시 로드한다.
