Feature Improvement Design Report

새로고침 처리 개선
기능 산출 보고서

작업 상태를 보존하면서 새로고침 의도를 제어하고, 취소 가능한 요청에만 취소 API를 호출하기 위한 구현 전 설계안

문서 통제 정보
작성 기준일 2026-09-01 문서 상태 구현 전 설계안
대상 영역 footer-comp.vue, Pinia, 키 이벤트, API 요청 상태 검증 경계 제공된 요구사항 기준. 대상 소스와 실행 결과는 미검증

결론

  1. 키보드 새로고침은 먼저 제어한다. F5, Ctrl+R, Cmd+R 입력을 감지해 현재 상태를 확인한 뒤 확인 또는 제한 안내를 표시한다.
  2. 취소 API는 다섯 조건이 모두 참일 때 한 번만 호출한다. 사용자 확인, 변경 존재, 취소 가능 상태, 취소 대상 식별자 존재, 취소 요청 대기 상태가 모두 필요하다.
  3. pagehide에서는 로그아웃·취소 API를 호출하지 않는다. 로그아웃은 사용자가 로그아웃을 명시적으로 선택한 경로에서만 수행한다.

01목적과 결정 범위

새로고침으로 세션이나 진행 중 작업이 비정상 종료되는 문제를 막기 위해, 입력 경로와 상태별 행동을 하나의 정책으로 고정한다.

문서를 작성하는 이유
배경 페이지에는 로컬 변경, 취소 가능한 요청, 취소할 수 없는 비동기 처리, 적용 작업이 함께 존재할 수 있다. 새로고침은 이 상태를 확인한 뒤 수행해야 한다.
현재 문제 제공된 현행 설명에서는 pagehide가 발생할 때 로그아웃 API를 호출한다. 새로고침과 페이지 종료를 구분하지 못하면 새 문서가 로드되기 전에 세션이 종료될 수 있다.
결정 사항 키보드 새로고침 처리, 상태 우선순위, 취소 API 호출식, pagehide 책임, 실패 시 이동 여부를 이 문서의 기준으로 사용한다.
문서의 한계. 현재 저장소에서 footer-comp.vue와 관련 Pinia 구현을 확인하지 못했으므로, 아래 내용은 코드 반영 결과가 아니라 구현 판단을 위한 설계 기준이다.

02현재 동작과 문제

문제의 핵심은 브라우저 수명주기 이벤트와 사용자 의도를 같은 것으로 취급하는 데 있다.

2.1 현재 처리

01사용자가 새로고침 또는 페이지 이동을 시작
02pagehide 발생
03로그아웃 API 호출
04세션 종료 후 새 문서 로드 시도

2.2 구체적인 문제

현행 문제와 발생 결과
문제원인발생 결과
의도 구분 실패 pagehide만으로 새로고침, 탭 닫기, 뒤로 가기를 안정적으로 구분할 수 없다. 단순 새로고침에도 로그아웃이 실행될 수 있다.
작업 상태 무시 로컬 변경, 비동기 처리, 적용 상태를 확인하기 전에 문서 이탈이 시작된다. 변경 유실 또는 처리 중단 가능성이 생긴다.
API 목적 혼합 페이지 수명주기와 사용자 로그아웃을 같은 API 경로에 연결한다. 새로고침이 세션 종료 행위로 바뀐다.
완료 순서 경쟁 네트워크 요청 완료 시점과 새 문서 이동 시점이 경쟁한다. 서버와 화면의 상태가 서로 다를 수 있다.

03변경안과 처리 흐름

사용자 입력을 먼저 감지하고 Pinia의 상태 스냅샷으로 행동을 결정한다. 페이지 수명주기 이벤트는 보조 경고에만 사용한다.

브라우저 메뉴·도구 모음·모바일 제스처. 키 이벤트를 거치지 않는 새로고침에는 조건부 beforeunload를 사용한다. 이 경로에서는 브라우저가 제공하는 기본 확인창만 사용할 수 있으며, 사용자가 이탈을 승인한 뒤까지 애플리케이션이 이동을 강제로 막을 수는 없다.

04상태별 처리 기준

동시에 여러 상태가 참이면 적용 중 → 비동기 처리 중 → 변경사항 있음 → 일반 순서로 하나의 분기를 선택한다.

4.1 상태 결정표

새로고침 및 API 처리
상태판정식새로고침처리
일반 hasUnsavedChanges === false
requestPhase === 'IDLE'		 확인 후 허용 키보드 경로에서는 확인창을 표시한다. 사용자가 승인하면 즉시 새로고침하며 API는 호출하지 않는다.
변경사항 있음 hasUnsavedChanges === true 조건부 허용 canCancel === true이면 취소 성공 뒤 새로고침한다. 로컬 변경만 있고 취소 대상이 없으면 폐기 확인 뒤 API 없이 새로고침한다.
비동기 처리 중 requestPhase === 'RUNNING' 제한 키보드 새로고침을 막고 “처리가 끝난 뒤 다시 시도해 주세요.”를 표시한다. 취소 API는 호출하지 않는다.
적용 중 requestPhase === 'APPLYING' 제한 키보드 새로고침을 막고 “변경사항을 적용하고 있습니다.”를 표시한다. 취소 API는 호출하지 않고 상태를 유지한다.

4.2 취소 API 호출 조건

아래 조건이 모두 참일 때만 취소 액션을 한 번 실행한다. 하나라도 거짓이면 취소 API를 호출하지 않는다.

shouldCallCancel =
  userConfirmed === true &&
  hasUnsavedChanges === true &&
  canCancel === true &&
  cancelTargetId !== null &&
  cancelRequestPhase === 'IDLE'
  • 호출 직전에 Pinia 상태를 다시 읽어 shouldCallCancel을 재계산한다.
  • 호출 시작과 동시에 cancelRequestPhase를 PENDING으로 바꾸고 반복 키 입력을 무시한다.
  • 서버 취소가 확인되면 cancelRequestPhase를 SUCCEEDED로 바꾼 뒤 한 번만 새로고침한다.
  • 실패 또는 시간 초과 시 FAILED로 바꾸고 새로고침하지 않는다. 오류 안내와 작업 상태를 그대로 유지한다.

4.3 Pinia 상태 계약

필수 상태와 의미
상태값의미
hasUnsavedChangesboolean화면에 서버 반영 전 변경이 하나 이상 있는지 표시한다.
requestPhaseIDLE | CANCELLABLE | RUNNING | APPLYING현재 작업의 취소 가능 여부와 새로고침 제한 단계를 나타낸다.
cancelTargetIdstring | null취소할 서버 작업 식별자다. 값이 없으면 취소 API를 호출하지 않는다.
cancelRequestPhaseIDLE | PENDING | SUCCEEDED | FAILED중복 취소 요청과 성공 전 새로고침을 막는다.
canCancel파생 booleanrequestPhase === 'CANCELLABLE' && cancelTargetId !== null로 계산한다.

05개발 영향

변경은 UI 이벤트, 전역 상태, API 수명주기, 세션 종료 책임에 걸쳐 있다.

구성요소별 변경 내용
대상변경완료 판단
footer-comp.vue 키 이벤트 등록·해제와 확인·제한 안내를 연결한다. pagehide의 로그아웃 호출을 제거한다. 컴포넌트가 해제된 뒤 이벤트 핸들러가 남지 않는다.
Pinia 상태 4.3의 상태와 우선순위 getter, 취소 액션, 새로고침 가능 여부 getter를 추가한다. 화면별 임시 값 없이 하나의 상태 판정 결과를 사용한다.
새로고침 키 이벤트 F5, Ctrl+R, Cmd+R을 캡처하고 기본 동작을 먼저 막는다. 동일 입력 한 번에 확인창 또는 제한 안내가 하나만 표시된다.
API 요청 상태 취소 요청을 IDLE → PENDING → SUCCEEDED/FAILED로 관리한다. PENDING 동안 같은 취소 API가 추가로 호출되지 않는다.
로그아웃 경로 로그아웃 API를 사용자 명시 동작에만 연결한다. 새로고침, 탭 닫기, 뒤로 가기에서 로그아웃 API 호출 건수가 0이다.

06예외와 리스크

브라우저가 보장하지 않는 영역은 애플리케이션 제어와 네이티브 경고의 경계를 분리해 대응한다.

예외 상황과 대응 기준
상황리스크대응
브라우저 메뉴 새로고침 키 이벤트가 발생하지 않는다. 보호 상태에서만 beforeunload를 등록하고 브라우저 기본 확인창을 사용한다.
Firefox 뒤로/앞으로 캐시 beforeunload 리스너가 성능과 캐시 사용에 영향을 줄 수 있다. 일반 상태에서는 리스너를 제거하고 변경·처리·적용 상태에서만 등록한다.
모바일 앱 전환·종료 beforeunload와 pagehide가 항상 발생한다고 보장할 수 없다. 필수 저장·로그아웃·취소를 수명주기 이벤트에 맡기지 않는다. 상태 복구는 별도 저장 전략으로 다룬다.
취소 중 반복 입력 취소 API가 중복 호출될 수 있다. cancelRequestPhase === 'PENDING'이면 추가 키 입력과 취소 호출을 무시한다.
판정 직후 상태 변경 비동기 작업이 RUNNING 또는 APPLYING으로 바뀔 수 있다. 확인 직후와 API 호출 직전에 우선순위와 취소 조건을 다시 계산한다.
취소 API 실패 서버 작업은 남고 화면만 새로고침될 수 있다. 실패·시간 초과에서는 새로고침하지 않고 오류와 재시도 경로를 표시한다.
제어 한계. beforeunload 확인창의 문구는 브라우저가 결정하며 사용자 지정 문구를 보장할 수 없다. 사용자 활성화가 없으면 확인창이 표시되지 않을 수 있으므로, 키보드 경로의 애플리케이션 확인창과 브라우저 기본 경고를 같은 기능으로 간주하지 않는다.

공식 참고자료: MDN · beforeunload, MDN · pagehide, WHATWG HTML · Browsing the web

07개발 범위와 인수 기준

구현 완료 여부는 상태별 결과와 API 호출 횟수로 판정한다.

7.1 개발 범위

  • footer-comp.vue: 키 이벤트, 확인·제한 안내, 수명주기 이벤트 정리
  • Pinia: 변경·요청·적용·취소 상태와 우선순위 getter
  • 새로고침 처리기: 단일 진입점, 반복 입력 잠금, 성공 뒤 한 번만 이동
  • API 요청 관리: 취소 대상 식별자, 요청 상태, 실패·시간 초과 처리
